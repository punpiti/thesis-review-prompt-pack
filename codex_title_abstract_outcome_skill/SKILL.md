# Thesis Title, Abstract, and Expected Outcome Review

Use this skill first whenever a title, abstract, expected outcome, expected
results, or contribution paragraph exists.

## Core Rule

This is a first-pass understanding review, not a final verdict on the whole
study. Keep this criticism separate from method/results criticism, especially
for early drafts.

## What To Check

1. Title
   - Does it name the real object/problem, not only a method or tool?
   - Is it too broad, too narrow, vague, overclaiming, or venue-inappropriate?
   - Does it imply a result or scope that the current draft cannot support?
   - If the user asks for alternatives, propose only evidence-consistent title
     directions: formal/technical, reader-facing/current, and
     outcome-oriented. Do not make the topic sound stronger than the evidence.

2. Abstract
   - problem
   - research gap
   - objective/RQ
   - method/approach
   - data/context
   - evaluation/result or expected result
   - contribution
   - limitation/scope signal when needed

3. Expected output vs expected outcome
   - Output: direct deliverable/evidence that the objective is met.
   - Outcome: downstream effect after the output is used or adopted.
   - Flag outcome claims that are not measured or not yet measurable.

4. Consistency
   - Title -> abstract -> expected output -> expected outcome
   - Any mismatch between stated problem, method, data, and contribution

5. Draft maturity
   - `early`: critique clarity and direction; do not require final results.
   - `middle`: require coherent problem/gap/method/evaluation direction.
   - `late`: require evidence-backed result and claim discipline.

## Output

Write a section in `04_review_notes/01_full_review.md` or a focused note if the
user asks only for this part:

```markdown
## Title / Abstract / Expected Outcome Review
### First-Pass Understanding
### Title
### Abstract
### Expected Output vs Expected Outcome
### Overclaims / Underclaims
### What Can Be Fixed Now
### What Requires Later Sections
```

Mark missing fields as `missing input`, not as failure.
